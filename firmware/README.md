# Cortex-M3 firmware

Build with `make` after sourcing `~/Microchip/setup-microchip-tools.sh`.
CMSIS, HAL, the MSS drivers, and the LCD driver come from the reference
project (see `sf2.mk` and `../libero/README.md`). The output,
`build/rppg.hex`, goes to `libero/build.tcl`.

| File | Purpose | Phase |
|------|---------|-------|
| `src/main.c` | Frame polling, ring buffer, buttons, DSP and UI calls | 2–4 |
| `src/uart.c` | UART to and from the PC through the PIC32 | 2, 4 |
| `src/console.c` | Text commands from the PC: LCD commands, test pattern, ROI | 4 |
| `src/drivers/ov7725.c` | Camera set-up; locks exposure and white balance | 1 |
| `src/dsp/rppg.c` | Normalization, POS, band-pass, FFT, peak pick | 3 |
| `src/ui/ui.c` | BPM digits, waveform, and quality bar on the LCD | 4 |
| `src/drivers/m5_hr.c` | M5 heart-rate unit over I2C | 5 |
| `src/dsp/bandpass_coeffs.h` | Generated by `tools/rppg/gen_coeffs.py` | 3 |
| `test/` | Host build of the DSP code | 3 |

## Timing on the board

An estimate runs in the main loop once a second (`ESTIMATE_EVERY` frames)
and takes 193 ms on the M3 at 100 MHz. Two things make it that fast:

- `main.c` turns on the instruction cache in front of the eNVM (`CC_CR`
  bit 0), which is off after reset. Without it, every instruction fetch waits
  for the eNVM, and an estimate takes 853 ms.
- `Makefile` builds `src/dsp/rppg.c` at `-O2`. At `-O0`, without the cache,
  an estimate takes 1.04 s: longer than the 1 s between estimates, so the
  frame queue in `main.c` overflows and the window keeps restarting.

The cache goes on after the camera and LCD set-up, because the reference
LCD driver times its delays with busy loops. Each `EST` line reports the
estimate time, so watch it when you add work to the main loop.

## The display

The fabric draws the BPM, a quality bar, and a scrolling waveform into the
camera image (`hdl/src/overlay.v`); `src/ui/ui.c` only writes its registers.
Estimates start at power-on, so the board works without a PC. The first one
comes after 10 s, the length of the window; until then the display shows
`---`.

- **Digits:** the smoothed BPM. After the first estimate, only estimates
  with quality at least `BPM_GATE_QUALITY` (the red end of the bar) move it,
  so the digits hold through bad windows instead of following them.
- **Waveform:** mean green over the ROI, high-passed and inverted so beats
  point up, about 5 s across. The SysTick handler updates it for every frame,
  so it keeps scrolling while an estimate runs. It autoscales to recent
  peaks, so movement shrinks the pulse until the peak decays (about 2 s).
- **Quality bar:** the estimate's peak power over in-band power, full at
  `QUALITY_FULL`, red below `QUALITY_LOW`, green from `QUALITY_GOOD`
  (`include/config.h`).
- **Mirroring:** the LCD shows the camera image mirrored, so `UI_MIRROR` is
  on. Turn it off if the digits read backwards.

## Buttons

The three buttons sit above the LCD; from left to right they are SW3, SW2,
and SW1 (silkscreen PB3_DEBUG, FF_SW2, PB1_DEBUG).

| Button | Action |
|--------|--------|
| SW1 (right) | Move the ROI to the next of nine positions, a 3 × 3 grid starting in the middle |
| SW2 (middle) | Change the ROI size: 160 × 120, 240 × 180, 96 × 72 (camera pixels) |
| SW3 (left) | Recalibrate the camera to the light: exposure, gain, and white balance adjust while the digits count down 3, 2, 1, then lock |

Moving the ROI or recalibrating restarts the estimates, so the display
shows `---` for 10 s (13 s after SW3). Don't press the buttons while
recording for `rppg.check_board`: the PC can't see the restart.

Recalibrate with SW3 after the light changes or after you sit down: the
camera then sets its exposure for your face rather than for whatever it saw
at power-up. A dim scene makes it raise the gain, and row noise then swamps
the pulse. The color test pattern moved to the console (`test 1`).

## Console

`python -m rppg.send <command> ...` (from `tools/`) sends commands over the
UART; `include/console.h` lists them. `lcd` sends a raw ILI9488 command: the
firmware takes the LCD bus from the video path for the few microseconds it
needs, so commands such as the gamma tables (`E0`, `E1`) can be tried
without a rebuild. `gain` and `color` try other color gains and overlay
colors the same way; copy values that work into `include/config.h`. All of
these last until the next power cycle.

`preview 1` makes the board send an 80 × 60 thumbnail of the camera (the
fabric's `thumb.v`), which `python -m rppg.preview` shows; `capture.py`
turns it off unless it runs with `--preview`. With the preview on, a
recording keeps every frame and its estimates still match the PC's
(`check_board`), and estimates still take 193 ms.

## Checking the DSP on the board

`python -m rppg.check_board session.csv` (from `tools/`) reruns the host
build over a recording from `capture.py` and compares every estimate with the
board's. `capture.py` sends `restart`, and the firmware restarts its
estimates at the next frame and reports it as `# restart <frame>`.
`capture.py` records from that frame on, so both see the same frames.

## Checking the DSP on the PC

`src/dsp/rppg.c` mirrors `tools/rppg/pos.py`. After you change either one, run
the comparison from `tools/`:

```bash
python -m rppg.check_firmware            # synthetic sessions, 45-230 bpm
python -m rppg.check_firmware rec.csv    # your own recordings
```

After you change `FRAME_RATE_HZ` or the HR band in `include/config.h`,
regenerate the filter with `python -m rppg.gen_coeffs`. The build fails with
an `#error` until you do. The HR band must also match `HR_BAND` in `pos.py`.
